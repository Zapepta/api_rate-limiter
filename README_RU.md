# in-memory tcp rate limiter

[English](README.md) | [Русский](README_RU.md)

---

Высокопроизводительный in-memory сервис ограничения частоты запросов (Rate Limiter), работающий поверх сырого TCP.
Спроектирован для работы в качестве сайдкар-контейнера в условиях жестких ресурсных ограничений (например, квота 0.5 CPU и лимит 30 МБ RAM в Linux cgroups).

## v1 против v2: Эволюция архитектуры

Первая версия (v1) была концептом, который выдавал красивые цифры в синтетических тестах, но имел фундаментальные изъяны при работе в реальной сети. Версия 2 — это полный архитектурный рефакторинг, устраняющий эти проблемы.

### 1. Структура памяти и Garbage Collector
* **Проблема v1:** Использовалась `map[string]*bucket`. Наличие строк и указателей в куче заставляло сборщик мусора (GC) сканировать миллионы объектов в фазе Mark. Это приводило к скачкам CPU и заморозке сервиса под нагрузкой.
* **Решение v2:** Переход на Zero-GC структуру `map[IPKey]bucketData`, где ключ — это плоский массив `[16]byte`, а значение — структура из примитивов. Отсутствие указателей позволяет рантайму Go полностью исключить мапу из сканирования GC.

### 2. Изоляция кэш-линий процессора (False Sharing)
* **Проблема v1:** Шарды хранились как массив указателей `[256]*shard`. Аллокатор Go размещал 16-байтные структуры вплотную друг к другу. В результате соседние шарды попадали в одну 64-байтную кэш-линию L1. Блокировка мьютекса на одном ядре сбрасывала кэш для других ядер.
* **Решение v2:** Шарды хранятся как непрерывный массив значений `[256]shard`. Заголовок хранилища и сами шарды выровнены паддингом `_ [48]byte` строго по границам 64 байт.

### 3. Защита от OOM и политика вытеснения
* **Проблема v1:** Хранилище росло бесконечно. Атака с 500 000 уникальных IP-адресов пробивала лимит в 30 МБ RAM, и ядро Linux убивало процесс (OOM-Killer).
* **Решение v2:** Введен жесткий лимит емкости шарда. При переполнении применяется алгоритм **O(1) Sampled Safe Eviction** (подобно Redis): проверяются до 3 случайных ключей, и вытесняется только тот клиент, чей баланс токенов полностью восстановился. Это защищает память и предотвращает блокировку легитимных пользователей под DDoS-атакой.

### 4. Фоновая очистка и CFS Throttling
* **Проблема v1:** Фоновая горутина раз в 5 секунд блокировала все 256 шардов для удаления старых записей. При квоте 0.5 CPU это мгновенно сжигало процессорный бюджет, вызывая CFS Throttling и сетевые задержки.
* **Решение v2:** Чистильщик работает инкрементально — обходит ровно 1 шард каждые 10 миллисекунд. Нагрузка на процессор размазана в незаметный фон.

### 5. Защита сетевого стека
* **Проблема v1:** Сервер был уязвим к атакам Slowloris, TCP Zero-Window (Sockstress) и исчерпанию файловых дескрипторов.
* **Решение v2:**
    * Внедрен семафор соединений (макс. 256) для защиты памяти ядра Linux.
    * Жесткий дедлайн 2 секунды на чтение первого байта (отстрел Slowloris).
    * Дедлайн 1 секунда на запись (защита от зависания TCP-окна).
    * Размер `bufio.Reader` уменьшен с 4 КБ до 128 байт для экономии RAM.

### 6. Синхронизация времени
* **Проблема v1:** Использовалось настенное время (`time.Now().UnixNano()`). Корректировка часов сервером NTP назад приводила к отрицательному балансу токенов.
* **Решение v2:** Переход на монотонный таймер (`time.Since()`).

## Подтвержденные метрики

**Примечание:** Приведенные ниже результаты получены на локальном тестовом стенде. Абсолютные показатели (нс/операцию, RPS) будут отличаться в зависимости от архитектуры процессора и операционной системы. При этом архитектурные показатели (0 аллокаций в хипе) остаются неизменными на любой платформе.

### 1. Ядро хранилища (Многопоточный бенчмарк)
```text
BenchmarkStorage_Warm_Allowed-8    53666302    19.92 ns/op     0 B/op    0 allocs/op
BenchmarkStorage_Cold_Insert-8     16132912    73.05 ns/op   166 B/op    0 allocs/op
BenchmarkStorage_Saturated_Evict-8 22885912    64.51 ns/op     1 B/op    0 allocs/op
```
* **Warm Path:** ~20 нс на проверку с 0 аллокаций в куче.
* **Saturated Eviction:** ~64 нс на проверку, что доказывает эффективность O(1) вытеснения при 100% заполнении памяти.

### 2. Сетевая пропускная способность (E2E)
10 000 запросов через 200 параллельных TCP Keep-Alive соединений:
```text
Allowed requests (+OK):   1000 (ожидалось: 1000)
Rejected (-ERR limit):    9000 (ожидалось: 9000)
Network errors:           0
Real network throughput:  161,864 req/s
```

### 3. Симуляция ботнета (500k уникальных IP)
Стресс-тест распределенной атаки с 500 000 уникальных IP по 50 параллельным потокам:
```text
Throughput under fire:  162,465 req/s
Allowed Bots (+OK):     256,000 (точный лимит емкости шардов)
Blocked Bots (-ERR):    244,000
Memory usage:           Зафиксировано на ~20 МБ (выжил в лимите 30 МБ)
```

## Запуск и тестирование

**Запуск сервера:**
```bash
go run ./cmd/server
```

**Запуск автономного E2E-теста:**
```bash
go test -v -run=TestEndToEndLoadAndCorrectness ./...
```

**Запуск бенчмарков ядра:**
```bash
go test -bench="." -benchmem -run="^#" ./internal/limiter
```

**Запуск внешнего стресс-теста:**
```bash
go run ./cmd/stress -c 200 -r 50
```

**Запуск симуляции ботнета (500k IP):**
```bash
go run ./cmd/botnet -bots 500000 -c 50
```
