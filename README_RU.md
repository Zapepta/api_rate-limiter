# in-memory tcp rate limiter

Высокопроизводительный In-Memory сервис ограничения частоты запросов (Rate Limiter), работающий поверх голого TCP на Go.

Проект разработан для исследования низкоуровневых паттернов конкурентности и сравнения архитектурных компромиссов между Sliding Window Log и Token Bucket при высокой конкуренции за мьютексы.

Параллельное тестирование ядра Token Bucket под нагрузкой из горутин (`b.RunParallel` на 8 потоках):

```text

BenchmarkStorage_Allow-8   111950100    11.31 ns/op    0 B/op    0 allocs/op
PASS
```

* **Задержка (Latency):** ~10–12 нс на проверку лимита на тестовом железе (~85–90 млн операций/сек).
* **Аллокации в heap:** 0 B/op (полное отсутствие выделений памяти на горячем пути `Allow`).

> **Примечание:** Результаты бенчмарков неизбежно будут отличаться в зависимости от архитектуры CPU, тактовой частоты, планировщика ОС и числа ядер. Ключевое архитектурное свойство системы — **0 allocs/op**, что гарантирует полное отсутствие пауз сборщика мусора (GC) на любом оборудовании.

## Архитектура и технические решения

### 1. Token Bucket вместо Sliding Window Log
Изначальный концепт предполагал использование Sliding Window Log со срезами таймстампов (`[]int64`). Однако постоянная очистка динамических слайсов под высоким RPS приводит к фрагментации памяти и чрезмерной нагрузке на Garbage Collector.
Я перешел на Token Bucket: состояние одного клиента описывается всего двумя полями — `tokens` (`float64`) и `lastUpdate` (`int64` unix nano). Начисление токенов происходит лениво (lazy evaluation) в момент входящего запроса на основе прошедшего времени. Это гарантирует сложность $O(1)$ по времени и фиксированные 16 байт памяти на клиента.

### 2. Шардирование мьютексов (Lock Striping)
Один глобальный `sync.RWMutex` создает жесткий Lock Contention при 1000+ параллельных горутинах. Поскольку операция проверки лимита изменяет состояние бакета, каждому запросу требуется эксклюзивная блокировка на запись (`Lock()`).
Хранилище разделено на 256 независимых шардов. Ключи распределяются по шардам с помощью хэш-функции FNV-1a. Массив организован как указатели `[256]*shard`, что предотвращает деградацию производительности из-за False Sharing (ложного разделения кэш-линий процессора).

### 3. Фоновая TTL-очистка
Для предотвращения бесконечного разрастания мапы от разовых IP-адресов реализован фоновый чистильщик. Чтобы исключить глобальную остановку сервиса (Stop-The-World), он блокирует и очищает каждый шард последовательно по отдельности, позволяя остальным шардам непрерывно обслуживать входящий сетевой трафик.

### 4. Сетевой транспорт и жизненный цикл
* Чтение идентификаторов клиентов происходит через постоянные TCP Keep-Alive соединения с использованием `bufio.Reader`.
* Graceful Shutdown обрабатывает системные сигналы `SIGINT`/`SIGTERM` через `signal.NotifyContext`. Соединения отслеживаются через `sync.WaitGroup`, что исключает разрыв активных сетевых сессий до завершения их обработки.

## Структура проекта

```text
cmd/server/main.go       - Точка входа и оркестрация жизненного цикла
internal/limiter/        - Шардированное хранилище и логика Token Bucket
internal/server/         - Цикл TCP-сервера и обработка протокола
load_test.go             - Интеграционный e2e стресс-тест (1000 клиентов, 10 000 запросов)
```

## Запуск и тестирование

### Запуск сервера
```bash
go run ./cmd/server
```

### Запуск бенчмарков ядра
```bash
go test -bench=. -benchmem ./internal/limiter/
```
*(В Windows PowerShell с обратными слэшами: `go test -bench=. -benchmem .\internal\limiter\`)*

### Запуск стресс-теста
Поднимает 1000 параллельных клиентов, отправляющих суммарно 10 000 запросов по TCP:
```bash
go test -v load_test.go
```
