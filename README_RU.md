# In-Memory Rate Limiter Daemon (v3)

[English](README.md) | [Русский](README_RU.md)

Высокопроизводительный сервис ограничения частоты запросов (L7 Rate Limiter) на Go с нулевыми аллокациями памяти на горячем пути. Работает по протоколам Unix Domain Sockets (UDS) и TCP. Спроектирован как легковесный sidecar-демон для автономной работы в жестких cgroup-лимитах контейнеров (1 vCPU, 24–30 МБ RAM).

---

## Архитектурная эволюция: от прототипа к production-ready sidecar

Проект прошел через три этапа разработки, каждый из которых устранял фундаментальные инженерные заблуждения:

```
+---------------------------------------------------------------------------------------------------+
| v1: Наивный прототип                                                                              |
| * map[string]*bucket + 256 наивных шардов.                                                        |
| * Фатальный изъян: «0 allocs/op» в README было иллюзией бенчмарка на прогретом пуле IP. Реальная   |
|   сеть аллоцировала память на каждый входящий TCP-запрос. Лимиты захардкожены в коде.             |
+---------------------------------------------------------------------------------------------------+
│
▼
+---------------------------------------------------------------------------------------------------+
| v2: Оверинжиниринг и псевдо-WAF                                                                   |
| * Честный Zero-GC (map[IPKey]bucketData, haspointers=false).                                      |
| * Фатальный изъян: Нарушение зон ответственности. Сервис попытался стать L7 WAF / анти-DDoS.       |
|   Динамическое схлопывание в /24 подсеть банило невинных пользователей за общим NAT/CGNAT.         |
|   Поведенческий скоринг раздул сложность без реальной пользы для устойчивости системы.            |
+---------------------------------------------------------------------------------------------------+
│
▼
+---------------------------------------------------------------------------------------------------+
| v3: Прагматичный Production Sidecar (Текущая версия)                                             |
| * Восстановлены архитектурные границы: лимитер работает как быстрый локальный турникет на входе. |
| * Детерминированный Backpressure: точный расчет времени ожидания в миллисекундах (Retry-After).   |
| * Дружелюбность к L1-кэшу: 256 компактных шардов (всего 4 КБ) целиком живут в L1D-кэше процессора.|
| * Сжатие памяти Go Map: пересоздание опустевших шардов для защиты от утечек памяти hmap в рантайме|
| * 12-Factor App дизайн: управление через CLI-флаги, ликвидация лишних файлов конфигурации.        |
+---------------------------------------------------------------------------------------------------+
```

### Что и почему было удалено из прошлых версий:
1. **Динамическое схлопывание подсетей `/24`:** Блокировка целых подсетей наносила сопутствующий ущерб (collateral damage) легитимным мобильным и корпоративным пользователям за NAT. Отражение распределенных ботнетов — задача периметра сети (Cloudflare, eBPF/XDP), а не локального микросервиса.
2. **Иллюзия защиты пула БД (Open-Loop vs Closed-Loop):** Алгоритм Token Bucket отслеживает входящую частоту запросов (RPS), но принципиально не видит глубину очереди транзакций и задержку (latency) базы данных. Физическую емкость пулов БД обязаны защищать семафоры параллелизма приложения (например, `max_open_conns`), а не токен-бакет по таймеру.
3. **Паддинг кэш-линий (Карго-культ):** Выравнивание шардов по 64 байта через пустые массивы `_ [48]byte` было вырезано. На 1 vCPU с `GOMAXPROCS(1)` межъядерная конкуренция (False Sharing) физически невозможна. Удаление паддинга сжало массив шардов в 4 раза (с 16 КБ до 4 КБ), позволив всем 256 шардам поместиться в L1D-кэш CPU.
4. **Побайтовое чтение из сокета:** Заменено на потоковый срез `ReadSlice('\n')` без аллокаций.

## Архитектура третьей версии (v3)

### 1. Детерминированный Backpressure (`Retry-After`)
Вместо отдачи неинформативного текста об ошибке, провоцирующего клиентов на агрессивный спам повторами (Retry Storm), движок вычисляет точное время в миллисекундах до пополнения баланса токенов:
$$\text{waitMs} = \left\lceil \frac{1.0 - \text{tokens}}{\text{refillRate}} \times 1000 \right\rceil$$
Сервер отдает статус `-ERR <retryAfterMs>\r\n`. Обратный прокси (Envoy, Nginx) или SDK приложения преобразуют это значение в стандартный заголовок HTTP `Retry-After: <sec>`, заставляя клиента корректно заснуть.

### 2. Структура памяти Zero-GC
Хранилище построено на шардированной `map[IPKey]bucketData`. Ключ `IPKey` (`[16]byte`) и данные `bucketData` (`tokens float64`, `lastUpdate int64`) состоят исключительно из скалярных типов без указателей. Рантайм Go маркирует внутреннюю хеш-таблицу флагом `haspointers=false`. Сборщик мусора (GC) полностью исключает данные лимитера из фазы сканирования кучи, устраняя GC-паузы.

### 3. Оптимизация под L1 Data Cache
Структура шарда избавлена от лишних полей и весит ровно 16 байт (мьютекс + указатель на мапу):
```go
type shard struct {
    mu      sync.Mutex
    buckets map[IPKey]bucketData
}
```
Все 256 шардов суммарно занимают ровно **4096 байт (одну страницу памяти 4 КБ)**. Это гарантирует, что таблица шардов постоянно находится в самом быстром L1D-кэше процессора (32–48 КБ).

### 4. Защита от фрагментации памяти мап в Go
Встроенная функция Go `delete()` освобождает ячейку, но никогда не сжимает массив корзин `hmap` в памяти. При всплеске трафика в 250 000 ключей мапы могли занять десятки мегабайт и вызвать падение контейнера по OOM (лимит 24 МБ). В v3 фоновый уборщик при полном устаревании ключей пересоздает мапу заново (`make(map[IPKey]bucketData)`), гарантируя физический возврат памяти операционной системе.

### 5. Сетевой конвейер и сокеты Unix (UDS)
* **Поддержка UDS:** Работа через `unix:///tmp/limiter.sock` устраняет весь оверхед сетевого стека ядра Linux (TCP handshake, сетевые буферы, порты) при работе в одном поде с приложением или Envoy.
* **Оппортунистический сброс буфера:** Сервер парсит входящие строки через `ReadSlice('\n')` и сбрасывает сетевой буфер (`writer.Flush()`) только тогда, когда входящий сокет пуст (`reader.Buffered() == 0`). Это склеивает пачки ответов в минимальное количество системных вызовов `write`.
* **Lock-Free Мониторинг:** Команда `STATS` возвращает атомарные счетчики (`Allowed`, `Rejected`, `Invalid`) без блокировок и без аллокаций памяти.

## Подтвержденные тесты и бенчмарки

> **Примечание:** Абсолютные показатели (`ns/op` и `req/s`) зависят от тактовой частоты CPU, микроархитектуры и планировщика ОС. Ключевой архитектурный инвариант системы — **0 allocs/op на стабильном горячем пути**, что гарантирует предсказуемый профиль задержек (predictable latency) и полное отсутствие давления на сборщик мусора (zero heap pressure) на любом оборудовании.

> Замерено на  13th Gen Intel(R) Core(TM) i3-13100F, Windows amd64, Go 1.25+.

## Как подбирать параметры `burst` и `rps`

* **`rps` (Refill Rate — Марафон):** Устойчивая скорость, с которой клиент может делать запросы часами.
* **`burst` (Capacity — Спринт):** Запас токенов на мгновенный рывок без штрафного ожидания.

### Практические сценарии:
1. **Frontend / SPA страницы:**  
   При открытии экрана браузер шлет пачку из 5–10 параллельных запросов (профиль, корзина, меню).  
   *Рекомендация:* `burst = 10–15`, `rps = 2–3`.
2. **Тяжелые эндпоинты (`/login`, `/register`, экспорт PDF):**  
   Защита процессора от выжигания сложной криптографией (`bcrypt`).  
   *Рекомендация:* `burst = 3–5`, `rps = 0.2` (1 попытка раз в 5 секунд).
3. **B2B API для сторонних интеграций:**  
   Устанавливается строго по тарифному плану клиента (например, `burst = 50`, `rps = 20`).

## Известные компромиссы и ограничения

1. **Эфемерное состояние в RAM:**  
   Счетчики хранятся исключительно в оперативной памяти. Перезапуск пода или пересоздание контейнера сбрасывает накопленные токены. Сайдкар спроектирован как быстрый локальный фильтр (node-local ingress pre-filter), а не распределенная общая база квот вроде Redis.
2. **Слепота к телу и заголовкам L7:**  
   Сервис является легковесным сетевым оракулом: принимает на вход готовую строку ключа (IP или хеш токена) и возвращает статус. Извлечение IP из заголовков `X-Forwarded-For` или JWT возлагается на вышестоящий прокси (Envoy, Nginx) или middleware приложения.
3. **Права доступа к Unix-сокетам:**  
   При создании UDS-файла выставляются права `0666`. Файл сокета должен размещаться в изолированном общем томе пода (`emptyDir`).

## Запуск и использование

Сервис построен по принципам 12-Factor App и управляется через стандартные CLI-флаги:

```text
Параметры запуска:
  -addr string
        TCP-адрес (:8080) или путь к UDS сокету (unix:///tmp/limiter.sock) (по умолчанию ":8080")
  -burst float
        Разрешенная емкость всплеска на клиента (по умолчанию 5.0)
  -rps float
        Скорость пополнения токенов в секунду (по умолчанию 1.0)
  -cap int
        Максимальная емкость одного шарда до включения LRU-вытеснения (по умолчанию 1000)
```

### Примеры запуска

#### Запуск по TCP (Локальная разработка и отладка)
```bash
go run ./cmd/server -addr :8080 -burst 10 -rps 2
```

#### Запуск по Unix Domain Socket (Боевой режим Sidecar)
```bash
go run ./cmd/server -addr unix:///tmp/limiter.sock -burst 20 -rps 5
```

#### Проверка по сети (Netcat)
```bash
# Проверка здоровья сервиса (Liveness Probe)
echo "PING" | nc 127.0.0.1 8080
# Ответ: +PONG

# Проверка лимита для ключа/IP
echo "192.168.1.1" | nc 127.0.0.1 8080
# Ответ при наличии токенов: +OK
# Ответ при превышении квоты: -ERR 450 (подождать 450 миллисекунд)

# Просмотр статистики без блокировок
echo "STATS" | nc 127.0.0.1 8080
# Ответ: +OK allowed=1000 rejected=9000 invalid=0
```

```bash
# Все интеграционные и юнит-тесты
go test -v ./...

# Бенчмарки горячего пути и аллокаций памяти
go test -run=^$ -bench="." -benchmem ./internal/limiter
```
