# In-Memory Rate Limiter Daemon (v3)

[English](README.md) | [Русский](README_RU.md)

Высокопроизводительный in-memory сервис ограничения частоты запросов (L7 Rate Limiter) на Go с нулевыми аллокациями памяти на горячем пути. Работает по протоколам TCP и Unix Domain Sockets (UDS). Спроектирован как легковесный sidecar-демон для работы в жестких cgroup-лимитах контейнеров (1 vCPU, 24–30 МБ RAM).

---

## Эволюция проекта

Проект прошел через три этапа разработки, каждый из которых вскрывал фундаментальные инженерные ошибки:

```
+---------------------------------------------------------------------------------------------------+
| v1: Наивный прототип                                                                              |
| * map[string]*bucket + 256 шардов без выравнивания кэш-линий.                                     |
| * Фатальный изъян: «0 allocs/op» было иллюзией синтетического микробенчмарка на прогретом пуле IP.|
|   Сетевой TCP-слой аллоцировал память на каждый запрос. False Sharing в структурах шардов.        |
+---------------------------------------------------------------------------------------------------+
│
▼
+---------------------------------------------------------------------------------------------------+
| v2: Оверинжиниринг и псевдо-WAF                                                                   |
| * Честный Zero-GC (map[IPKey]bucketData, haspointers=false), паддинг кэш-линий (64 байта).        |
| * Фатальный изъян: Нарушение зон ответственности. Сервис попытался стать WAF/анти-DDoS фильтром.  |
|   Динамическое схлопывание в /24 подсеть привело к бану невинных клиентов за общим NAT/CGNAT.    |
|   Эвристика «нервных кликеров» раздула сложность, но не спасала емкость бэкенда.                  |
+---------------------------------------------------------------------------------------------------+
│
▼
+---------------------------------------------------------------------------------------------------+
| v3: Прагматичный Production Sidecar (Текущая версия)                                             |
| * Архитектурные границы восстановлены: лимитер применяет чистую математику, а не гадает намерения.|
| * Двухуровневый Token Bucket: глобальная защита бэкенда (БД) + квоты на клиентов.                 |
| * Поддержка Unix Domain Sockets (UDS), батчинг сетевого I/O, валидатор конфигураций в стиле -t.   |
+---------------------------------------------------------------------------------------------------+
```

### Что было вырезано из v2 и почему
1. **Динамическое схлопывание подсетей в `/24`:** В v2 при перегрузке шарда IPv4-адреса объединялись в подсети `/24`. Это было грубой ошибкой: отражение распределенных атак ботнетов — задача L3/L4 (eBPF, XDP, Cloudflare), а не локального демона. Схлопывание приводило к *сопутствующему ущербу (collateral damage)* — один спамер банил всех пользователей мобильного оператора или офиса за тем же NAT.
2. **Поведенческий анализ и «Limp Mode»:** Попытки профилировать «нервных кликеров» и насильно урезать burst до 1.0 превращали математический сервис в непредсказуемый «черный ящик». В v3 это полностью ликвидировано: сервис работает детерминированно.
3. **Искаженный FNV-1a хэш:** Чтобы реализовать схлопывание в `/24`, v2 намеренно пропускала 15-й байт IPv4 при вычислении хэша. В v3 алгоритм FNV-1a считает честную энтропию по всем 16 байтам.
4. **Побайтовое чтение из сокета:** Цикл с `ReadByte()` создавал лишний оверхед на вызовы функций рантайма. Заменен на zero-alloc срез `ReadSlice('\n')`.

## Архитектура третьей версии (v3)

### 1. Двухуровневый Token Bucket (Two-Tier Guard)
Вместо эвристической борьбы с ботнетами v3 решает задачу защиты инфраструктуры математически:
* **Уровень клиента (Client Tier):** Шардированный token bucket, изолирующий клиентов друг от друга (`client_burst`, `client_rps`).
* **Уровень бэкенда (Backend Capacity Guard):** Глобальный token bucket, отражающий реальную физическую емкость нижележащей системы (`backend_burst`, `backend_rps` рассчитываются исходя из пула соединений PostgreSQL, PgBouncer или допустимой p95 latency). Даже если миллион уникальных ботов сделают по 1 запросу, они не положат базу данных — их срежет глобальный лимит.

### 2. Структура памяти Zero-GC
Хранилище построено на `map[IPKey]bucketData`. Поскольку ключ `IPKey` (`[16]byte`) и данные `bucketData` (`tokens float64`, `lastUpdate int64`) состоят исключительно из скалярных типов без указателей, рантайм Go присваивает мапе флаг `haspointers=false`. Сборщик мусора (GC) **полностью исключает мапу из фазы сканирования**, что предотвращает GC-паузы под нагрузкой.

### 3. Изоляция шардов и защита от False Sharing
Хранилище разбито на 256 независимых шардов. Каждая структура `shard` дополнена паддингом в 48 байт:
```go
type shard struct {
    mu      sync.Mutex
    buckets map[IPKey]bucketData
    _       [48]byte // Выравнивает структуру точно под 64-байтную кэш-линию CPU
}
```
Это исключает взаимную инвалидацию кэш-линий процессора соседними ядрами при одновременной блокировке разных шардов.

### 4. Unix Domain Sockets и батчинг сетевого I/O
* **Поддержка UDS:** Работа через `unix://./rate-limiter.sock` устраняет весь оверхед сетевого стека ядра Linux (loopback TCP) при развертывании sidecar-контейнера в одном поде с приложением или Envoy/Nginx.
* **Оппортунистический сброс буфера:** Сервер парсит строки через `ReadSlice('\n')` и вызывает `writer.Flush()` только тогда, когда буфер входящего сокета пуст (`reader.Buffered() == 0`). При пачке запросов ответы склеиваются в минимальное число системных вызовов `write`.

## Подтвержденные тесты и бенчмарки

> **Примечание:** Абсолютные показатели (ns/op и req/s) зависят от тактовой частоты CPU, архитектуры и планировщика ОС. Ключевое архитектурное свойство системы — **0 allocs/op на стабильном горячем пути**, что гарантирует отсутствие фрагментации кучи и деградации по вине GC на любом сервере.

**Тестовый стенд:** 13th Gen Intel(R) Core(TM) i3-13100F, Windows amd64, Go 1.25+.

### 1. Микробенчмарки ядра хранилища
```text
go test -run=^$ -bench="." -benchmem .\internal\limiter
```
```text

BenchmarkStorage_Warm_Rejected-8        58031007        20.36 ns/op        0 B/op    0 allocs/op

BenchmarkStorage_Saturated_Eviction-8   16472451        89.96 ns/op        3 B/op    0 allocs/op
```
* **Горячий путь (Warm):** ~20–21 нс на одну проверку лимита при **0 B/op и 0 allocs/op**.
* **Холодный путь (Cold):** Штатные аллокации рантайма Go при первичном расширении бакетов хеш-мапы под новые IP.
* **Режим вытеснения (Eviction):** Под перегрузкой алгоритм O(1) Sampled LRU (семплирование 8 элементов) тратит ~90 нс на операцию без блокировки всего сервиса.

## Известные ограничения и архитектурные минусы (Честный разбор)

Ради экстремальной скорости и укладывания в лимит 24–30 МБ памяти были допущены следующие компромиссы:

1. **Уязвимость перед Slowloris / Исчерпание соединений:**
    * Сервер держит семафор на `maxConnections = 256`.
    * Если 256 клиентов откроют соединения и будут слать байты крайне медленно (укладываясь в 15-секундный `idleTimeout`), пул соединений будет полностью занят. 257-й клиент получит мгновенный разрыв связи.
    * **Решение:** Сервис **обязан** стоять за реверс-прокси (Envoy, Nginx, HAProxy), который агрегирует соединения, обрубает медленных клиентов (Slowloris protection) и терминирует TLS.
2. **Эфемерное состояние в RAM:**
    * Все токены хранятся исключительно в оперативной памяти. Перезапуск процесса или пода мгновенно сбрасывает все счетчики, предоставляя нарушителям временную амнистию.
3. **Неатомарность между клиентом и бэкендом (Lock Ordering):**
    * Для проверки запроса сначала берется мьютекс конкретного шарда `sh.mu`, а затем глобальный мьютекс `s.globalMu`. Это исключает дедлоки, но на экстремальных частотах в сотни тысяч RPS глобальный мьютекс может создавать микроконтеншн.
4. **Слепота к L7-заголовкам и токенам:**
    * Сервер принимает на вход только IP-адреса и команду `PING`. Он не парсит HTTP-заголовки, куки или JWT — эта обязанность целиком возлагается на вышестоящий шлюз.
5. **Права доступа к Unix-сокетам:**
    * При создании UDS-файла выставляются права `0666`. В мульти-тенант окружениях путь к сокету должен быть изолирован на уровне каталогов и прав контейнера.

## Конфигурация (`rate-limiter.conf`)

Сервис поддерживает предварительную проверку валидности конфига (по аналогии с `nginx -t`):

```ini
network = tcp          # 'tcp' или 'unix'
addr    = :8080        # Порт ':8080' или сокет './rate-limiter.sock'

# Лимиты нижележащей системы (DB Connection Pool / downstream capacity)
backend_burst = 5.0    # Размер пула соединений БД (PostgreSQL max_connections / PgBouncer)
backend_rps   = 140.0  # Максимальный устойчивый RPS до деградации p95 latency базы

# Квоты отдельного клиента
client_burst  = 2.0    # Разрешенный burst на одного клиента
client_rps    = 1.0    # Скорость пополнения токенов в секунду
```

### Защитные механизмы конфига:
* Отсекает значения `NaN` и `Inf`.
* Анализирует соотношения: если `client_burst >= backend_burst`, выводит критическое предупреждение о том, что один клиент может монополизировать весь пул базы данных.
* Требует интерактивного подтверждения `[y/N]` при запуске в терминале или явного флага `-force` для безголовых сред (Docker/K8s).

## Запуск и эксплуатация

### Запуск сервиса
```bash
go run ./cmd/server -config rate-limiter.conf
```

### Проверка валидности конфигурации (Pre-flight check)
```bash
go run ./cmd/server -config rate-limiter.conf -t
```

### Принудительный запуск в CI/Docker
```bash
go run ./cmd/server -config rate-limiter.conf -force
```

### Запуск тестов и бенчмарков ядра
```bash
# Все юнит- и E2E-тесты
go test -v ./...

# Бенчмарки наносекунд и аллокаций
go test -run=^$ -bench="." -benchmem ./internal/limiter
```

### Проверка по сети (Healthcheck / Netcat)
```bash
# Проверка здоровья (K8s liveness probe)
echo "PING" | nc 127.0.0.1 8080
# Ответ: +PONG

# Проверка лимита IP
echo "192.168.1.1" | nc 127.0.0.1 8080
# Ответ: +OK или -ERR Rate limit exceeded
```
