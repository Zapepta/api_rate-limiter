# in-memory tcp rate limiter

[English](README.md) | [Русский](README_RU.md)

---

Высокопроизводительный in-memory сервис ограничения частоты запросов (Rate Limiter), работающий поверх сырого TCP на Go.
Спроектирован как легковесный **L7 Decision Engine / Сайдкар** (концептуально аналогичен Envoy Rate Limit Service) для работы в условиях жестких ресурсных ограничений (**1 ядро CPU через `GOMAXPROCS=1`, лимит 30 МБ памяти в Linux cgroups**).

## Границы ответственности: чем сервис является (и чем не является)

* **Decision Engine, а не сквозной прокси:** Демон сам не проксирует пользовательский трафик и не парсит прикладные HTTP-запросы. Входящий шлюз (Envoy, Nginx, Traefik) обращается к демону по постоянному TCP Keep-Alive соединению, передавая идентификатор клиента (IPv4, IPv6, API-токен или Tenant ID), и получает мгновенное решение `+OK` или `-ERR`.
* **Контроль частоты по сущностям:** Защищает нижележащий сервис от агрессивных скраперов, брутфорса авторизации, повторных штормов клиентов (retry storms) и обеспечивает честное деление квот (Fair Share).
* **Защита от голодания ресурсов (Anti-Starvation):** Гарантирует, что при полном заполнении шардов мусорным трафиком легитимные пользователи не блокируются наглухо и получают ответ с задержкой менее 1 миллисекунды.
* **Разделение зон ответственности:** Защита от распределенных атак высокой кардинальности (миллионы уникальных IP с 1 запросом) должна решаться на уровне Edge-инфраструктуры (Cloudflare, Anycast BGP, eBPF/XDP или глобальные лимиты кластера).

## v1 против v2: Эволюция архитектуры

Первая версия (v1) была концептом, который хорошо показывал себя в синтетических тестах, но содержал критические уязвимости при реальной сетевой нагрузке. Версия 2 — это полный архитектурный рефакторинг.

### 1. Структура памяти и Garbage Collector
* **Проблема v1:** Использовалась `map[string]*bucket`. Наличие строк и указателей в куче заставляло сборщик мусора (GC) сканировать миллионы объектов в фазе Mark. Это приводило к скачкам CPU и деградации задержек.
* **Решение v2:** Переход на Zero-GC структуру `map[IPKey]bucketData`, где ключ — это плоский массив `[16]byte`, а значение — структура из примитивов. Отсутствие указателей позволяет рантайму Go выставить флаг `haspointers=false`, полностью исключая мапу из сканирования GC.

### 2. Изоляция кэш-линий процессора (False Sharing)
* **Проблема v1:** Шарды хранились как массив указателей `[256]*shard`. Аллокатор Go размещал 16-байтные структуры вплотную друг к другу. В результате соседние шарды попадали в одну 64-байтную кэш-линию L1. Блокировка мьютекса на одном ядре сбрасывала кэш для других ядер CPU.
* **Решение v2:** Шарды хранятся как непрерывный массив значений `[256]shard`. Заголовок Storage и сами шарды выровнены паддингом `_ [48]byte` строго по границам 64 байт.

### 3. Защита от OOM и политика вытеснения
* **Проблема v1:** Хранилище росло бесконечно. Атака высокой кардинальности (500 000 уникальных IP) пробивала лимит 30 МБ памяти, и ядро Linux убивало процесс (OOM-Killer).
* **Решение v2:** Введен жесткий лимит емкости шарда. При переполнении применяется алгоритм **O(1) Sampled LRU Eviction**: проверяются до 3 случайных ключей и вытесняется самый неактивный бакет. При заполнении шарда на $\ge 90\%$ burst-квота подавляется до 1.0 токена, сглаживая лавинообразные всплески нагрузки.

### 4. Фоновая очистка (CFS Throttling)
* **Проблема v1:** Горутина чистильщика раз в 5 секунд блокировала все 256 шардов залпом для удаления старых записей. Это вызывало скачки CPU и сетевые микропаузы.
* **Решение v2:** Чистильщик работает инкрементально — проверяет ровно 1 шард каждые 10 миллисекунд (полный цикл 2.56 с). Фоновая нагрузка на CPU ограничена незаметными ~0.03% одного ядра.

### 5. Защита сетевого стека
* **Проблема v1:** Уязвимость к Slowloris, TCP Zero-Window (Sockstress) и исчерпанию соединений.
* **Решение v2:**
    * Семафор соединений (макс. 256) защищает память сокетов ядра Linux.
    * Жесткий дедлайн 2 секунды на чтение первого байта (отстрел Slowloris).
    * Дедлайн 1 секунда на запись (защита от Sockstress).
    * Размер `bufio.Reader` уменьшен с 4 КБ до 128 байт для экономии RAM на соединение.

### 6. Синхронизация времени
* **Проблема v1:** Использовалось настенное время (`time.Now().UnixNano()`), при скачках которого из-за NTP токены уходили в минус.
* **Решение v2:** Расчет токенов переведен на монотонный таймер `time.Since(processStart)`.

## Подтвержденные метрики

> **Примечание к бенчмаркам:** Результаты зависят от процессора, тактовой частоты и планировщика ОС (замеры сделаны на **13th Gen Intel(R) Core(TM) i3-13100F, Windows amd64**). Ключевое архитектурное свойство системы — **0 allocs/op** на горячем пути, гарантирующее отсутствие пауз GC на любом оборудовании.

### 1. Ядро хранилища (Многопоточный бенчмарк)
```text
BenchmarkStorage_Warm_Allowed-8        50040657    20.81 ns/op      0 B/op    0 allocs/op
BenchmarkStorage_Warm_Rejected-8       58953276    19.71 ns/op      0 B/op    0 allocs/op
BenchmarkStorage_Cold_Insert-8         20229639    60.27 ns/op    132 B/op    0 allocs/op
BenchmarkStorage_Saturated_Eviction-8  21449176    73.76 ns/op      3 B/op    0 allocs/op
```
* **Warm Path:** ~20 нс на операцию (~50 млн оп/сек) с 0 аллокаций в куче на 10 000 активных клиентов.
* **Cold Path:** ~60 нс на первичное создание бакета.
* **Saturated Eviction:** ~73 нс при 100% заполнении шардов, подтверждая, что $O(1)$ Sampled LRU вытеснение добавляет минимальный оверхед.

### 2. Сетевая пропускная способность по TCP (`load_test.go`)
10 000 запросов через 200 параллельных TCP Keep-Alive соединений:
```text
Allowed requests (+OK):   1000 (ожидалось: 1000)
Rejected (-ERR limit):    9000 (ожидалось: 9000)
Network errors:           0
Burst duration:           60.58ms
Real network throughput:  165,060 req/s
```

### 3. Тест на устойчивость к голоданию под осадой (`cmd/siege`)
Заливка хранилища 300 000 уникальных IP ботов по 50 параллельным потокам при одновременных запросах реального пользователя (1 запрос раз в 1.2 секунды):
```text
Время теста:             7.23с
Обработано ботов:        498 122 запроса
Запросов юзера (+OK):    6 / 6 (100% успеха)
Задержка юзера:          0.5мс - 1.0мс
Память:                  Зафиксировано на ~20-22 МБ (внутри лимита 30 МБ)
```

## Структура проекта

```text
cmd/server/main.go       - Точка входа демона, настройка GOMAXPROCS(1) / GOMEMLIMIT
cmd/stress/main.go       - CLI-утилита стресс-тестирования пропускной способности
cmd/botnet/main.go       - Симулятор атаки высокой кардинальности (500k уникальных IP)
cmd/siege/main.go        - Стресс-тест устойчивости к голоданию (DDoS + реальный юзер)
internal/limiter/        - Шардированное ядро хранения, Zero-GC типы, инкрементальный чистильщик
internal/server/         - Сетевой TCP-сервер, компактный ридер, семафор соединений
load_test.go             - Автономный интеграционный e2e-тест
```

## Запуск и тестирование

**Запуск сервера:**
```bash
go run ./cmd/server
```

**Запуск автономного E2E-теста:**
```bash
go test -v -run=TestEndToEndLoadAndCorrectness .\load_test.go
```

**Запуск бенчмарков ядра:**
```powershell
go test -bench="." -benchmem -run="^#" .\internal\limiter
```

**Запуск внешнего стресс-теста:**
```bash
go run ./cmd/stress -c 200 -r 50
```

**Запуск теста под осадой (DDoS + юзер):**
```bash
go run ./cmd/siege
```

**Запуск симуляции атаки ботнета (500k IP):**
```bash
go run ./cmd/botnet -bots 500000 -c 50
```
