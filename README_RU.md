# In-Memory Rate Limiter Daemon (v3.1)

[English](README.md) | [Русский](README_RU.md)

Высокопроизводительный сервис ограничения частоты запросов (L7 Rate Limiter) на Go с нулевыми аллокациями памяти на горячем пути. Работает по протоколам Unix Domain Sockets (UDS) и TCP. Спроектирован как легковесный sidecar-демон для работы в жестких cgroup-лимитах контейнеров (1 vCPU, 24 МБ RAM).

---

### Архитектурные решения и исправления
1. **Защита от межъядерной конкуренции (False Sharing):** Структура каждого шарда выровнена паддингом до 64 байт (`_ [32]byte`). Таблица из 256 шардов занимает 16 КБ. Это исключает межъядерную инвалидацию L1/L2 кэша при масштабировании на несколько vCPU без искусственного зажима в один поток через `GOMAXPROCS(1)`.
2. **Безопасное вытеснение (Lossless Eviction):** Стандартный LRU в rate-лимитерах порождает уязвимость: атакующий ротацией случайных IP забивает шард, вытесняя оштрафованные бакеты, которые при повторном входе получают полный запас токенов. Алгоритм v3.1 сэмплирует кандидатов и вытесняет тех, у кого баланс токенов восстановился до максимума ($curTokens \ge maxTokens$).
3. **Защита от фрагментации хеш-таблиц Go:** Внутренний механизм Go `delete()` освобождает ячейку, но никогда не сжимает массив корзин `hmap`. Непрерывный цикл «вытеснение $\to$ вставка» при перегрузке плодит цепочки overflow-корзин. Демон отслеживает число вытеснений и пересоздает мапу при превышении лимита ($\ge 128$).
4. **Математическая синхронизация TTL:** Интервал очистки рассчитывается исходя из физики пополнения корзин:
   $$\text{TTL} = \max\left(5\text{с}, \min\left(24\text{ч}, \left\lceil \frac{\text{maxTokens}}{\text{refillRate}} \right\rceil \text{с}\right)\right)$$
   Это исключает преждевременное удаление оштрафованных клиентов при низких скоростях пополнения (`rps`).

## Архитектура ядра

### 1. Детерминированный Backpressure (`Retry-After`)
Сервер вычисляет точное время в миллисекундах до восстановления баланса токенов:
$$\text{waitMs} = \left\lceil \frac{1.0 - \text{tokens}}{\text{refillRate}} \times 1000 \right\rceil$$
Ответ `-ERR <waitMs>\r\n` транслируется обратным прокси (Envoy, Nginx) в стандартный HTTP-заголовок `Retry-After: <sec>`.

### 2. Структура памяти Zero-GC
Хранилище разделено на 256 независимых шардов: `map[IPKey]bucketData`.
* `IPKey` — скалярный массив `[16]byte` (IPv4 транслируется в `::ffff:a.b.c.d`).
* `bucketData` содержит исключительно скалярные типы (`float64`, `int64`).
Поскольку структуры не содержат указателей, рантайм Go маркирует память мапы флагом `haspointers=false`. Сборщик мусора полностью исключает данные лимитера из фазы сканирования, предотвращая GC-паузы.

### 3. Структура шарда
```go
type shard struct {
    mu          sync.Mutex           // 8 байт
    buckets     map[IPKey]bucketData // 8 байт (указатель на hmap)
    peakEntries int                  // 8 байт
    evictions   int                  // 8 байт
    _           [32]byte             // 32 байта паддинга до 64-байтной кэш-линии
}
```
Каждый шард занимает ровно 64 байта (размер кэш-линии современных процессоров x86-64 и ARM64). Таблица заголовков занимает ровно **16 384 байта (16 КБ)**, а данные записей хранятся в несканируемой куче.

### 4. Сетевой конвейер и контроль соединений
* **Поддержка UDS и TCP:** Работа через сокет Unix (`unix:///tmp/limiter.sock`) или TCP (`:8080`).
* **Неблокирующий пул соединений:** Жесткий лимит на 256 одновременных подключений. При насыщении пула новые соединения мгновенно сбрасываются без блокировки основного цикла accept, инкрементируя атомарный счетчик `dropped`.
* **Оппортунистический сброс буфера:** Сброс сетевого буфера в сокет (`writer.Flush()`) происходит только тогда, когда входящий буфер пуст (`reader.Buffered() == 0`). Это склеивает конвейерные ответы в минимальное количество системных вызовов `write(2)`.
* **Lock-Free телеметрия:** Команда `STATS` форматирует метрики без аллокаций памяти в куче через стек и `strconv.AppendUint`.

* **Вытеснение под перегрузкой:** ~94 нс на операцию. Периодическое сжатие мап амортизируется на тысячи запросов и не создает нагрузки на GC в steady-state режиме.

## Компромиссы и эксплуатационные ограничения

1. **Эфемерное локальное состояние:** Счетчики хранятся исключительно в оперативной памяти инстанса. Перезапуск контейнера сбрасывает квоты. Сайдкар спроектирован как высокопроизводительный локальный фильтр, а не распределенная база квот (вроде Redis).
2. **Агрегация IPv6 в подсети `/64`:** Входящие IPv6-адреса маскируются до `/64` (за исключением лупбека `::1`) для защиты от исчерпания памяти атаками с частой сменой адресов по SLAAC Privacy Extensions.
3. **Отсутствие парсинга заголовков L7:** Сервис является сетевым оракулом: принимает готовую строку IP или токена. Извлечение реального IP из заголовка `X-Forwarded-For` или JWT должно выполняться вышестоящим прокси (Envoy, Nginx).

## Запуск и использование

Управление осуществляется через стандартные CLI-флаги (12-Factor App):

```text
Параметры запуска:
  -addr string
        TCP-адрес (:8080) или путь к UDS сокету (unix:///tmp/limiter.sock) (по умолчанию ":8080")
  -burst float
        Разрешенная емкость всплеска на клиента (по умолчанию 5.0)
  -rps float
        Скорость пополнения токенов в секунду (по умолчанию 1.0)
  -cap int
        Максимальная емкость одного шарда до включения вытеснения (по умолчанию 1000)
```

### Примеры запуска

#### Запуск по TCP
```bash
go run ./cmd/server -addr :8080 -burst 10 -rps 2
```

#### Запуск по Unix Domain Socket (Sidecar-режим)
```bash
go run ./cmd/server -addr unix:///tmp/limiter.sock -burst 20 -rps 5
```

#### Проверка протокола
```bash
# Проверка жизнеспособности (Liveness Probe)
echo "PING" | nc 127.0.0.1 8080
# Ответ: +PONG

# Проверка квоты для IP
echo "192.168.1.1" | nc 127.0.0.1 8080
# Ответ при наличии токенов: +OK
# Ответ при превышении квоты: -ERR 450 (подождать 450 мс)

# Мониторинг без блокировок и аллокаций
echo "STATS" | nc 127.0.0.1 8080
# Ответ: +OK allowed=1000 rejected=9000 invalid=0 dropped=0
```

go test -v ./...
