# In-Memory TCP Rate Limiter

[English](README.md) | [Русский](README_RU.md)

Высокопроизводительный in-memory L7 rate-limiter, работающий поверх сырого TCP на Go. Спроектирован как легковесный decision engine для работы в условиях жестких ресурсных ограничений (например, 1 vCPU, лимит 30 МБ памяти в cgroups).

## Архитектурные компромиссы и механика

Проект создан как R&D-исследование пределов рантайма Go, управления памятью и сетевого стека в экстремально сжатых границах.

### 1. Структура памяти Zero-GC
Для выживания в лимите 30 МБ при высокой ротации соединений хранилище полностью исключено из зоны видимости Garbage Collector.
Состояние хранится в `map[IPKey]bucketData`, где `IPKey` — плоский массив `[16]byte`, а `bucketData` содержит только скалярные значения. Из-за отсутствия указателей компилятор Go устанавливает флаг `haspointers=false`, полностью пропуская мапу при сканировании памяти. Это гарантирует **0 allocs/op** на горячем пути.

### 2. Схлопывание подсетей при перегрузке (Graceful Degradation)
Классический per-IP лимитер математически слеп к распределенному трафику высокой кардинальности (ботнет из 100 000 IP по 1 запросу). Для предотвращения исчерпания памяти и вымывания кэша (Cache Churn) применяется динамическое маскирование:
* **Штатный режим:** Лимиты считаются по `/32` (индивидуальный IPv4).
* **Режим перегрузки:** При заполнении шарда на 90% трекинг IPv4 динамически схлопывается до подсети `/24` (`lookupKey[15] = 0`).
* **Компромисс:** Атакующие из одного пула прокси/датацентра группируются в один бакет и мгновенно блокируются. Легитимные пользователи, сидящие за общим NAT внутри атакуемой `/24` подсети, столкнутся с временной деградацией сервиса (Limp Mode). Это осознанная жертва ради спасения бэкенда от каскадного отказа.

### 3. Выравнивание дисперсии шардов
Хранилище разбито на 256 шардов через хэш FNV-1a для минимизации конкуренции за мьютексы. Чтобы схлопывание в `/24` работало корректно, алгоритм хэширования игнорирует 15-й байт для IPv4. Это гарантирует, что все 256 адресов одной подсети `/24` попадут строго в один и тот же мьютекс.

### 4. Поведенческий UX и подавление Burst-трафика
В режиме перегрузки burst-квота (`maxTokens`) жестко урезается до 1.0.
* **Умные клиенты** (с UI-debounce или поддержкой `Retry-After`) сохраняют высокий процент успешных запросов.
* **Нервные пользователи (Rage Clickers)**, спамящие запросами при ошибке, мгновенно сжигают токены, устраивают себе Self-DoS и жестко блокируются.

## Подтвержденные метрики

> **Примечание к бенчмаркам:** Абсолютные значения пропускной способности (ns/op и req/s) неизбежно зависят от архитектуры процессора, тактовой частоты и планировщика ОС (тесты проведены на 13th Gen Intel Core i3-13100F, Windows amd64). Ключевое архитектурное свойство системы — **0 allocs/op на горячем пути (steady-state)**. Это полностью исключает фрагментацию кучи и предотвращает непредсказуемые всплески задержек от сборщика мусора (GC) на любом оборудовании и в любых cgroups-лимитах.

**Зачем здесь эти метрики и что они доказывают:**
Эти тесты приведены не для хвастовства наносекундами. Их цель — экспериментально доказать заявленные архитектурные инварианты:
1. **Горячий путь (`Warm_Allowed`/`Rejected`):** Доказывает отсутствие аллокаций (`0 allocs/op`). Как только клиент попадает в мапу, обновление его токенов не требует выделения памяти в куче, что позволяет сборщику мусора «спать».
2. **Холодный путь (`Cold_Insert`):** Показывает ожидаемую стоимость и базовые аллокации рантайма при расширении хэш-мапы Go для новых IP-адресов.
3. **Режим перегрузки (`Saturated_Eviction`):** Доказывает, что алгоритм вытеснения O(1) Sampled LRU и схлопывание в `/24` подсеть добавляют минимальный оверхед (всего ~50 нс) и не приводят к деградации пропускной способности ядра под атакой.

## Известные ограничения и компромиссы (Trade-offs)

Ради достижения экстремальной производительности в рамках 30 МБ памяти были сделаны осознанные архитектурные жертвы:

1. **Сопутствующий ущерб (CGNAT):** Схлопывание до `/24` подсети спасает бэкенд от ботнетов, но временно ограничивает легитимных пользователей, сидящих за общим NAT (мобильные операторы, корпоративные сети) вместе с атакующим.
2. **Эфемерное состояние:** Хранилище работает исключительно в оперативной памяти. Любой рестарт контейнера или деплой полностью стирает историю нарушителей, давая им чистый лист и временную амнистию.
3. **Нестандартный протокол:** Ради экономии памяти и нулевых аллокаций используется кастомный текстовый TCP-протокол (`+OK` / `-ERR`). Для интеграции с Nginx/Envoy потребуется писать свой Lua/WASM-скрипт, так как сервис не поддерживает стандарты gRPC (Envoy RLS) или RESP (Redis).
4. **Отсутствие Observability:** Проект создавался как R&D-прототип вычислительного ядра. В нем нет экспорта метрик (Prometheus), проб (health checks) и структурированного логирования, что делает его «черным ящиком» для SRE-инженеров в реальном проде.
5. **Слепота к L7-контексту:** Движок оперирует только IP-адресами. Он не умеет лимитировать по HTTP-заголовкам, JWT-токенам или API-ключам, если только вышестоящий шлюз сам не извлечет их и не передаст в виде плоской строки.

## Структура проекта

```text
cmd/
  server/       - Точка входа демона
  stress/       - Out-of-process бенчмарк пропускной способности
  simulator/    - Симулятор поведенческого UX и трафика
internal/
  limiter/      - Zero-GC хранилище, FNV-1a хэширование, логика схлопывания подсетей
  server/       - TCP-сервер, микробуферы, защита от дедлоков
load_test.go    - Автономный интеграционный E2E-тест
```

## Запуск и тестирование

**Запуск сервера:**
```bash
go run ./cmd/server
```

**Запуск автономного E2E-теста:**
```bash
go test -v .\load_test.go
```

**Запуск бенчмарков ядра:**
```bash
go test -bench="." -benchmem .\internal\limiter
```

**Запуск внешнего стресс-теста:**
```bash
go run ./cmd/stress -c 200 -r 50
```

**Запуск поведенческой симуляции трафика:**
```bash
go run ./cmd/simulator
```
